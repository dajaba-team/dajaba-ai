# 07. LLM 기법 선택과 이유

코드가 아니라 판단 기록. 발표 "왜 이렇게 설계했나" 슬라이드의 재료. 준영도 읽으면 좋다.

## 문제의 성격부터

입력은 이미 구조화된 facts(숫자·날짜·계좌·유형). 출력은 형식이 정해진 6개 섹션. 최대 위험은 **없는 숫자·사실을 지어내는 것**이고, 어려운 추론은 거의 없다. 그러니 기법은 "추론을 돕는 것"이 아니라 **"제약을 지키게 하는 것"**을 골랐다.

## 기법별 판단

| 기법 | 우리 문제에서 | 판단 |
|---|---|---|
| Structured Output (JSON 스키마 강제) | 섹션 6개 각 1회·`cites` 형식을 모델이 아니라 스키마가 보장 | **채택.** 핵심 |
| Grounded generation (fact 인용 강제, FACTS 밖 금지) | "지어내기"를 구조로 막음. 섹션마다 `cites`에 fact 키, 목록 밖 키 금지. **거래 ID는 LLM이 고르지 않고 코드가 cites에서 연결**(10/27 — ID 목록을 주면 아무 ID나 옮겨 적는다) | **채택** |
| Few-shot (유형별 예시 3개) | 문체·형식 고정. 같은 유형 1 + 다른 유형 2 | **채택** |
| LLM-as-Judge (별도 평가자, 루브릭 5·4·3·1점) | 코드가 못 보는 추측·단정·완결성. 통과선 4점의 기준을 적어 둠 | **채택.** 평가자는 **comment 먼저, score 나중** — 사실상 짧은 CoT. 입력은 생성기와 같은 마스킹 facts(평가자는 숫자 대조를 안 한다) |
| Chain of Thought (답 전에 생각 쓰기) | 수학·다단계 추론용. 여기선 추론 단계가 없고, 생각 텍스트가 JSON에 섞일 위험 + 토큰 2~3배 | **생성기에는 안 씀.** 평가자의 comment-first만 |
| Generate → Check → Revise (검증 실패를 피드백으로 1회 재생성) | 자동 수정률이 올라감. 좋은 후보 | **MVP 보류.** "fail이면 조사역이 고친다"라 흐름이 단순하고, 재생성이 숫자를 또 바꿀 위험. 10/27 회의에서 초안·검증 분리(안건 17)로 더 멀어짐 |
| RAG (참고 사례 검색) | 10/14 "코퍼스 없음"으로 제외 → **10/26 범위 고정해 1차 포함**(안건 22). 유형 설명을 구체적으로, 조사역이 출처 인용 가능 | **채택(범위 고정).** 생성 품질용이고 검증 대체가 아님. 상세 `10` |
| Plan-then-write (개요 먼저) | facts 자체가 개요 | 불필요 |
| Self-consistency (N번 생성해 투표) | 비용 N배, 보고서 초안엔 과함 | 불필요 |
| Fine-tuning | 정답 STR이 없음 | 불가 |
| 에이전트 프레임워크 (LangChain·LangGraph) | 파이프라인이 LLM 호출 2번(생성·평가자)의 직선. 추상화 계층만 늘고 버전 변경에 깨짐 | **안 씀.** SDK 직접 + Pydantic. RAG도 pgvector + numpy로 충분. 2차에 코퍼스가 커지면 다시 판단 |

## 관측과 모델 설명을 섞지 않기 (10/27)

1차 검토가 잡은 설계 오류: 점수 `reasons`의 SHAP 기여값을 `"distinct_senders_24h = 31"`처럼 관측값인 듯 facts에 넣고 있었다. 기여값은 "모델이 이 피처에 얼마나 기댔나"지 "그 피처의 값"이 아니다. 그래서 facts를 `observations[]`(값·단위·기간·기준값 — 준영 안건 3 구조에서 가져옴)와 `model_signals[]`(피처 이름만)로 나눴다. LLM은 전자로 "평소 3.4개 → 31개"를 쓰고, 후자로 "모델이 주목한 항목" 한 줄만 쓴다. 발표에서 "설명가능성"을 말할 때 이 구분을 그대로 쓴다.

## 재현성

- 온도 0, 모델 ID 고정(`.env`), 프롬프트 파일 해시·few-shot id·참고 사례·임베딩 모델을 `generations`에 기록. "같은 입력에 facts는 항상 같고 narrative만 다를 수 있다"가 설계 목표(규약 6.4).
- 모델 교체는 `.env` 한 줄 + 오류 주입 7~12 표 다시 돌리기. 코드 변경 없음.

## 비용 (초안 1건, 대략)

| 호출 | 입력 토큰 | 출력 토큰 |
|---|---|---|
| 생성 (facts + few-shot 3 + references 3) | 3,000~4,500 | 800~1,200 |
| 평가자 | 2,000~3,000 | 300~500 |
| 임베딩 (질의 1회) | ~50 | — |

하루 한도 `LLM_DAILY_TOKEN_BUDGET`, 시연 전날 리셋. 실측은 W4에 `generations`로 뽑아 여기 갱신.

## 시간 (가정값 — W2 수요일 첫 실측 뒤 고침)

초안 1건 80초 예산 안에 LLM 호출 1회 35초, 스키마 실패 재생성은 남은 예산이 40초 이상일 때만(`03`). 숫자 셋은 측정 전 가정이고, 측정 뒤 `domain/constants.py`와 `03`·`09`를 같이 고친다. AI 안에서 연결 재시도는 하지 않는다 — 백엔드 1회와 겹치면 실질 4회가 되고 90초를 넘긴다.

## 발표에서 솔직하게 말할 것

- 평가자 점수는 사람 평가와 "대체로" 일치하는지만 확인한다(5건). 정답 보고서가 없어 절대 품질은 못 잰다.
- RAG 코퍼스는 영문 FATF·FinCEN 공개 문서다. KoFIU 참고유형 사례집은 비공개라 못 썼다(`10`).
- 합성 데이터라 고객명·기관명 마스킹이 느슨하다. 실데이터면 `masking.py`가 바뀌는 자리다.
