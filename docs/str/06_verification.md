# 06. 검증 — 코드 검사 5종(유형별 대조) + 평가자 5종 (10/27 개정, SCRUM-47 7항목 공존)

정본: `str/domain/verification.py` `run_code_checks(facts, narrative, evidence_scope) -> list[CodeCheck]`(순수), `str/infrastructure/judge.py` `Judge.run(facts_masked, narrative) -> list[LlmCheck]`(실패는 예외 → service가 status로), `str/prompts/judge_v1.md`, `shared/hashing.py`. passed·status 계산은 `application/verify_service.py`.

원칙 두 줄: **숫자·날짜·계좌·근거는 코드가 본다**(LLM이 뭐라고 해도 코드가 잡은 건 실패). **서술 품질(완결성·일관성·추측·단정)은 LLM 평가자가 본다**, 코드가 통과한 다음에만.

**섹션 집합 두 가지 (SCRUM-47)** — 코드 검사·해시는 **v1(6개)·v2(7개) 둘 다 받는다**. 반영일 전 승인본·초안을 보존하기 위함. 집합 보고 어느 쪽인지 판단(섹션 이름이 겹치지 않음). 섞인 응답은 거부(해시 ValueError, 생성 스키마 검증 실패). 두 집합 모두에 공통인 유형별 대조(`AMOUNT_MATCH` 등)는 섹션 이름과 무관하게 돈다. **종합의견 공란 검사 `OPINION_PRESENT` 는 v2 집합에만** 돈다.

코드 검사가 하는 일의 경계 (규약 5.3 문구 그대로): **지원하는 표현에서 추출한 사실값을 해당 유형의 facts와 대조한다.** 추출 못 한 표현은 `match=false, reason=UNPARSED`로 드러낸다 — 조용히 통과시키지 않는다. 의미적 타당성("이 금액이 이 문장에 맞나")은 평가자·사람 몫. "본문의 모든 숫자를 검증한다"고 말하지 않는다(2차 검토 4번).

## 코드 검사 (`domain/verification.py`) — 유형별 대조

1차 검토 2번·5번 반영: 숫자를 "금액이냐 아니냐"로 나누던 것을 버리고, **본문에서 뽑은 값의 유형**(금액+통화, 날짜, 건수, 상대 수, 계좌 식별자)마다 facts의 **해당 유형 값**과만 대조한다. 결과 하나 = `{check, section, draft_value, source_value, match, reason}` (`reason`은 `match=false`일 때만: `MISMATCH` / `UNPARSED` / `OUT_OF_SCOPE` / `MISSING`). 섹션마다 돈다. 전부 순수 함수, LLM 없음, 정규식과 Decimal. 상수(정규식·단위·허용 집합)는 `domain/constants.py`.

`LLM_MODEL_JUDGE` 가 **비었거나 생성 모델(`LLM_MODEL_GENERATE`)과 같으면 기동 때 경고 한 줄** — `log.warning("judge_model_fallback", extra={"generate": <모델>, "judge": <모델 또는 "">, "reason": "EMPTY"|"SAME"})`. 모델 이름만 찍고 다른 비밀은 없다. 폴백 자체는 **유지**(비어 있어도 서버는 뜬다 — 평가자가 생성 모델로라도 돈다). `AI_LLM_MOCK=true` 면 모델을 안 쓰므로 경고 없음(테스트·CI 로그 덮임 방지). 아래 "평가자가 자기 글을 채점하는 문제" 와 같은 뜻 — 경고가 "다른 모델로 두라" 는 알림이다. **`LLM_MODEL_JUDGE` 는 생성기와 다른 OpenAI 모델**로 두는 것이 원칙(SCRUM-61 ★A, 09 2026-11-05 결정) — 같은 OpenAI 라 `HttpLlmClient` 재사용 가능하고 "자기 글 너그러움" 을 피함.

### 1회 재시도 (SCRUM-92, 11/4)

평가자 호출이 **스키마 실패**(`LlmInvalidOutput`)면 남은 예산 안에서 **1회만** 다시 부른다. **그 외 모든 예외**(연결·타임아웃 `LlmUnavailable`·일 토큰 한도 등)는 재시도하지 않고 바로 올라와 `VERIFY_UNAVAILABLE` 로 끝난다 — 35초 타임아웃을 한 번 더 기다리면 백엔드 공유 90초를 넘기고, 조사역이 "다시 검증" 을 누르는 흐름이 이미 있음(안건 9). 남은 예산이 `LLM_TIMEOUT_S`(35초) 미만이면 재시도하지 않고 바로 `LlmUnavailable("verify budget exceeded")` 로 올려 `VERIFY_UNAVAILABLE` 로 끝난다 — draft 의 예산 초과 처리와 같은 모양(`str/03` "예산 초과는 LlmUnavailable"). 예산은 verify 요청 시작에 `verify_service` 가 정하고(`str/03` 시간 예산 표) `Judge` 는 남은 시간만 본다 — `domain/` 은 시계를 만지지 않는다(`01`). 두 번 다 스키마 실패면 호출은 **2번**(3번 아님), `LlmInvalidOutput` 그대로 올라와 `VERIFY_UNAVAILABLE`. 실패한 1번째 시도의 토큰·지연도 합산해 저장한다(비용 추적 NFR-APR-03). **SCRUM-144 (2026-11-05)**: 2차가 스키마가 아닌 다른 예외(연결 `LlmUnavailable`·HTTP 4xx `LlmInvalidOutput`·`BudgetExceeded`·예상 못 한 예외) 로 끝나도 같은 규칙 — 1차 결과가 있으면 그 값으로 `judge_meta` 를 붙여 던지고, `verify_service` 가 DB 에 남긴다. `judge_attempts` 는 **보낸 호출 수**(2), `judge_latency_ms` 는 결과 받은 호출만(실패 호출 지연은 `judge_unavailable` 로그로만).

### 모델·토큰 기록 (SCRUM-92, 11/4)

평가자 호출 메타는 `verification_runs` 같은 행의 다섯 칸에 — `judge_llm_model`(OpenAI 가 돌려준 모델명 또는 녹화면 `"recorded"`), `judge_tokens_in`·`judge_tokens_out`(**시도 전체 합**), `judge_latency_ms`(시도 전체 합), `judge_attempts`(1 또는 2). 응답에는 **같은 값을 `judge_meta: JudgeMeta | null`** 로 담는다 — `JudgeMeta { llm_model, prompt_version, tokens_in, tokens_out, latency_ms, attempts }`. 이름은 초안 응답 `GenerationMeta` 와 맞춤(`shared/04`). **PASSED·LLM_FAILED 는 채우고**, `CODE_FAILED`·`VERIFY_UNAVAILABLE` 은 응답 `judge_meta=null`(평가자 결과가 "쓸 값" 이 아니므로 — `llm_checks` 와 같은 규칙). 단 **`VERIFY_UNAVAILABLE` 인데 1번째 시도가 스키마 실패로 토큰을 쓴 경우 DB 에는 그 토큰까지 포함해 남긴다** — 응답에는 null, 저장은 유지(감사·비용 추적). 백엔드 `AiDtos.VerifyResponse.raw(JsonNode)` 가 모르는 필드를 통째로 담아 `FAIL_ON_UNKNOWN_PROPERTIES` 영향 없음 — DTO 변경 없이도 깨지지 않는다.

## passed·status (안건 9 확정)

code_ok   = all(c.match for c in code_checks)

## 수정본 길이와 글자 수 (노션 백엔드 미결 24, 규약 §5.3 — 10/30 확정)

- **생성**(`NarrativeOut`, LLM 출력)은 섹션당 1~1,200자 그대로. **검증 요청의 수정본**(조사역이 고친 본문)은 스키마를 따로 두고 섹션당 **최대 5,000자** — 백엔드가 5,000자까지 저장하므로 생성 스키마로 검증하면 1,201~5,000자 수정본이 400이 된다.
- 글자 수는 **NFC로 정규화한 뒤 UTF-16 코드 단위**로 센다 — Java `String.length()`·JS `.length`와 같은 값. Python `len()`·Pydantic `max_length`는 코드포인트라 쓰지 않는다(예: `len(unicodedata.normalize("NFC", s).encode("utf-16-le")) // 2`). 한글·영문은 어느 방식이든 같고, 이모지처럼 BMP 밖 문자만 2로 세진다. 맥에서 NFD로 들어온 한글도 NFC로 바꾼 뒤 세므로 한 글자 = 1.
- NFC는 **세기 위해서만** 쓴다. 해시는 원래대로 `shared/01` 규칙(NFC 포함)이고, 공백 strip은 하지 않는다(10/29 SCRUM-16).
- 경계 테스트(양쪽 리포 같은 값): **5,000자 통과 · 5,001자 400 · "4,999자 + 이모지 1개" 400**(5,001로 셈). 구현은 SCRUM-46.
- 구현 위치: `shared/schemas/str/narrative.NarrativeSectionBase`(공통 부모) + `shared/schemas/str/verify.RevisedNarrativeSection`(5,000자, `_text_within_revised_max`), 세기 함수 `shared/text.utf16_len_nfc`, 상수 `shared/schemas/str/verify.REVISED_TEXT_MAX`. `VerifyRequest.narrative`는 `list[RevisedNarrativeSection]`.

## 본문 해시 (`shared/hashing.py`)

검증 응답의 `narrative_sha256`. 규칙은 `shared/01`(섹션 고정 순서, section·text만, NFC, 공백 없는 JSON, sha256 hex). 백엔드 `ApprovalGate`는 `generation_id` 일치 + 본문 해시 일치 + `passed` 세 조건일 때만 승인 요청 허용(`str/03`) — 해시만 같으면 다른 생성본(다른 facts)의 검증이 통할 수 있다. 테스트 벡터 `contracts/examples/narrative_hash.json`을 Python이 만들고 Java가 맞춘다(W3).

## 평가자가 자기 글을 채점하는 문제

생성 모델과 같은 모델이면 너그럽다. 대책: ① `LLM_MODEL_JUDGE`를 다른 모델로(비거나 같으면 **기동 경고 한 줄** — 위 "모델" 절, SCRUM-92) ② 같은 모델이면 system 첫 줄 "당신은 이 초안을 쓴 사람이 아니라 검수자입니다" ③ comment 먼저 쓰게 하기. W4에 사람 평가 5건과 비교해 "대체로 일치"를 확인하는 게 MVP 정의서 4절 6번의 "됐다".

## 수정본의 cites·evidence_ids — (a) 확정 (안건 23 세부, 채영 "반영 가능", 10/28 문서 반영 · SCRUM-61 11/5 활성)

조사역이 본문을 고치면 생성 때의 `cites`는 더 맞지 않을 수 있다. 그래서 검증할 때 근거를 **다시 계산해 돌려준다**.

1. 평가자 `judge_v2`가 루브릭 5개와 함께 섹션별 `cites`(검사한 본문이 실제로 쓴 fact 키)를 낸다(`05`). **sections 섹션 집합은 요청 본문과 정확히 같게**(v1 6 또는 v2 7, 섹션마다 1회) — 다르면 `LlmInvalidOutput` → 기존 1회 재시도(SCRUM-92) → 실패면 `VERIFY_UNAVAILABLE`(SCRUM-61 ★A 1).
2. 코드가 `fact_keys(draft.facts)` **밖** 키를 버리고 `attach_evidence(요청 본문 text + 버린 뒤 cites, facts)`로 `evidence_ids`를 만든다 — 생성 때와 같은 함수. **버린 키는 `log.warning("judge_cites_dropped", extra={"section": …, "count": …})` 로 한 줄만**(섹션당 한 번, 키 이름·본문 안 찍음 — CLAUDE.md 로그 금지어, SCRUM-61 ★A 3). 응답 모양은 그대로(규약 5.3 변경 없음).
3. 검증 응답 `narrative_refs: [{section, cites, evidence_ids}]`(**요청 섹션 순서 유지**, v1 6 또는 v2 7)에 담는다. **빈 cites 허용**(평가자가 그 섹션엔 근거 없다고 판단). 평가자를 안 돌린 경우(`CODE_FAILED` — 코드 검사에서 멈춤, `VERIFY_UNAVAILABLE` — 평가자 호출 실패)는 `null`. **`LLM_FAILED`** 는 **값 있음**(평가자는 돌았음, 점수가 미달일 뿐).
4. 백엔드(채영)는 `narrative_refs`가 오면 그 값을 수정본 저장에 반영하고, `null`이면 기존 값을 유지한다. 조사역은 문장만 고치고 근거 번호는 서버가 관리한다.

본문 해시는 section·text만 보므로 `cites`가 바뀌어도 `ApprovalGate`에는 영향이 없다. `EVIDENCE_IN_SCOPE` 코드 검사는 그대로 요청에 담긴 수정본의 `cites`·`evidence_ids`를 본다(재계산 전 값). 테스트: 재계산 결과가 범위 안인지, 목록 밖 키가 버려지는지, `CODE_FAILED`·`VERIFY_UNAVAILABLE`이면 `null`·`LLM_FAILED` 면 값 있음인지(`08` 단위).

## 요약에 도는 코드 검사 (SCRUM-129, 2026-11-06)

`/v1/cases/summary` 응답 `summary_lines[≤6]` 을 **한 덩어리 본문**으로 코드 검사 4종만 돌린다 — `AMOUNT_MATCH`·`DATE_MATCH`·`COUNT_MATCH`·`ACCOUNT_ID_MATCH`. `run_code_checks(facts, [SummarySection(section=None, text="\n".join(summary_lines), evidence_ids=req.evidence_transaction_ids)], req.evidence_transaction_ids)`. `EVIDENCE_IN_SCOPE`·`OPINION_PRESENT` 는 안 돌림 — 요약 줄에 `cites` 가 없고(규약 §6.1 응답 모양 — `cites` 칸 없음), facts 가 `evidence_transaction_ids` 로만 계산되므로 숫자 범위 밖 거래 생성 불가(IF-CASE-02 "허용 거래 대조"는 이걸로 충족). OPINION 섹션은 초안 v2 전용.

**평가자(LLM 검사)는 안 돌림** — 요약은 보조 정보라 40초 예산 안에서 코드 검사만. 품질은 코드 검사 + 재생성 1회로.

**실패 처리 (★A 3)**: 코드 검사 실패 → 남은 예산 ≥ `REGEN_MIN_REMAINING_S` 면 재생성 1회. 두 번 다 실패면 **200 + `code_checks.match=false` 담아 반환**. 백엔드가 "검증 통과분만 저장"(`case_summaries.payload`, 지윤·채영) — 틀린 요약은 화면에 안 띄움. `generations` 행은 `kind=SUMMARY·status=SUCCEEDED`(응답은 돌려줬으므로).

**`model_focus` 숫자 거부 (★A 4)**: `summary_service` 가 `model_signals` 이름을 **글자 그대로 지운 뒤 남은 글자에 숫자(0~9) 가 있을 때만** `null` 로 바꿈 — 이름 자체가 `account_in_counterparties_24h` 처럼 숫자 포함이어도 그 이름만 썼으면 통과, 이름 밖에 "3건"·"24시간" 같은 관측 수치가 섞이면 거부. `log.warning("summary_model_focus_rejected", extra={"reason":"non_signal_digit"})` — 본문·숫자 안 찍음.
