정본: `str/domain/verification.py` `run_code_checks(facts, narrative, evidence_scope) -> list[CodeCheck]`(순수), `str/infrastructure/judge.py` `Judge.run(facts_masked, narrative) -> list[LlmCheck]`(실패는 예외 → service가 status로), `str/prompts/judge_v1.md`, `shared/hashing.py`. passed·status 계산은 `application/verify_service.py`.

**섹션 집합 두 가지 (SCRUM-47)** — 코드 검사·해시는 **v1(6개)·v2(7개) 둘 다 받는다**. 반영일 전 승인본·초안을 보존하기 위함. 집합 보고 어느 쪽인지 판단(섹션 이름이 겹치지 않음). 섞인 응답은 거부(해시 ValueError, 생성 스키마 검증 실패). 두 집합 모두에 공통인 유형별 대조(`AMOUNT_MATCH` 등)는 섹션 이름과 무관하게 돈다. **종합의견 공란 검사 `OPINION_PRESENT` 는 v2 집합에만** 돈다.

코드 검사가 하는 일의 경계 (규약 5.3 문구 그대로): **지원하는 표현에서 추출한 사실값을 해당 유형의 facts와 대조한다.** 추출 못 한 표현은 `match=false, reason=UNPARSED`로 드러낸다 — 조용히 통과시키지 않는다. 의미적 타당성("이 금액이 이 문장에 맞나")은 평가자·사람 몫. "본문의 모든 숫자를 검증한다"고 말하지 않는다(2차 검토 4번).

설계 선택:
- **거짓 양성을 감수한다.** 못 읽은 표현을 `UNPARSED`로 떨어뜨리면 조사역이 문장을 숫자 형태로 고치면 된다. 놓치는 쪽(지어낸 금액 통과)이 훨씬 비싸다.
- **허용 오차 0.** `320,000,000 US Dollar`와 `3억 2천만 US Dollar`는 같은 Decimal이라 통과, `약 3억 US Dollar`은 `UNPARSED`. **소수 3자리 이상도 같은 규칙** — facts `"0.004200"` + 본문 `"0.0042 BTC"` 는 `Decimal("0.004200") == Decimal("0.0042")` 라 통과(SCRUM-140, 11/7). 본문 `"0.004 BTC"` 는 `Decimal("0.004") ≠ Decimal("0.0042")` 라 `MISMATCH`. 금액 문자열 자릿수 규칙은 `str/04` "금액 문자열 규칙".
- 뽑는 표현이 늘면(`천만 원` 등) 표에 한 줄 추가 + 테스트 한 줄. 표에 없는 표현은 "지원 안 함"이고 그걸 숨기지 않는다.
- **감지 못 하는 표현은 코드 검사 범위 밖이다.** 숫자도 한글 수사 패턴도 아닌 것(`수십 개`, `열댓 건`, `대부분`, `한 주 동안`)은 코드가 보지 않는다 → `NO_UNSUPPORTED_CLAIM` 평가자와 조사역·승인자 몫. 위 경계 문구("지원하는 표현에서 추출한…")가 이 뜻이다.
- 다섯 개 전부 W3 마지막 — AMOUNT·ACCOUNT SCRUM-58(11/2), DATE SCRUM-59(11/3), COUNT SCRUM-60(11/4), EVIDENCE·OPINION 상시(SCRUM-57·47).
- **narrative_v4(SCRUM-228)의 슬롯·카탈로그 문장은 이 표 규칙을 지나도록 코드가 만든다** — 검사기는 그대로, 못 지나면 문형을 바꾼다(05 narrative_v4 절, 정상·변조 표는 08).

## 평가자 (`infrastructure/judge.py`, `prompts/judge_v1.md`)

입력 **마스킹한 facts** + narrative(`text`만). 출력 5개 `{check, comment, score 1~5}` — comment가 score보다 앞. 온도 0. 통과선이 4점이므로 **4점의 뜻을 적는다**(2차 검토 반영 — 기준 없는 4점은 5와 3 사이 임의값이 된다).

### 모델 (SCRUM-92, 11/4)

`LLM_MODEL_JUDGE` 가 **비었거나 생성 모델(`LLM_MODEL_GENERATE`)과 같으면 기동 때 경고 한 줄** — `log.warning("judge_model_fallback", extra={"generate": <모델>, "judge": <모델 또는 "">, "reason": "EMPTY"|"SAME"})`. 모델 이름만 찍고 다른 비밀은 없다. 폴백 자체는 **유지**(비어 있어도 서버는 뜬다 — 평가자가 생성 모델로라도 돈다). `AI_LLM_MOCK=true` 면 모델을 안 쓰므로 경고 없음(테스트·CI 로그 덮임 방지). 아래 "평가자가 자기 글을 채점하는 문제" 와 같은 뜻 — 경고가 "다른 모델로 두라" 는 알림이다. **`LLM_MODEL_JUDGE` 는 생성기와 다른 OpenAI 모델**로 두는 것이 원칙(SCRUM-61 ★A, 09 2026-11-05 결정) — 같은 OpenAI 라 `HttpLlmClient` 재사용 가능하고 "자기 글 너그러움" 을 피함.

### 1회 재시도 (SCRUM-92, 11/4)

평가자 호출이 **스키마 실패**(`LlmInvalidOutput`)면 남은 예산 안에서 **1회만** 다시 부른다. **그 외 모든 예외**(연결·타임아웃 `LlmUnavailable`·일 토큰 한도 등)는 재시도하지 않고 바로 올라와 `VERIFY_UNAVAILABLE` 로 끝난다 — 35초 타임아웃을 한 번 더 기다리면 백엔드 공유 90초를 넘기고, 조사역이 "다시 검증" 을 누르는 흐름이 이미 있음(안건 9). 남은 예산이 `LLM_TIMEOUT_S`(35초) 미만이면 재시도하지 않고 바로 `LlmUnavailable("verify budget exceeded")` 로 올려 `VERIFY_UNAVAILABLE` 로 끝난다 — draft 의 예산 초과 처리와 같은 모양(`str/03` "예산 초과는 LlmUnavailable"). 예산은 verify 요청 시작에 `verify_service` 가 정하고(`str/03` 시간 예산 표) `Judge` 는 남은 시간만 본다 — `domain/` 은 시계를 만지지 않는다(`01`). 두 번 다 스키마 실패면 호출은 **2번**(3번 아님), `LlmInvalidOutput` 그대로 올라와 `VERIFY_UNAVAILABLE`. 실패한 1번째 시도의 토큰·지연도 합산해 저장한다(비용 추적 NFR-APR-03). **SCRUM-144 (2026-11-05)**: 2차가 스키마가 아닌 다른 예외(연결 `LlmUnavailable`·HTTP 4xx `LlmInvalidOutput`·`BudgetExceeded`·예상 못 한 예외) 로 끝나도 같은 규칙 — 1차 결과가 있으면 그 값으로 `judge_meta` 를 붙여 던지고, `verify_service` 가 DB 에 남긴다. `judge_attempts` 는 **보낸 호출 수**(2), `judge_latency_ms` 는 결과 받은 호출만(실패 호출 지연은 `judge_unavailable` 로그로만).

### N회 중앙값 — verify 경로만 (SCRUM-207, 2026-11-12)

같은 본문을 N 번 채점해 **항목별 중앙값** 으로 판정한다 (`JUDGE_VOTES=3`, `str/domain/constants`). run 간 흔들림(SCRUM-147 같은 본문 TYPO 5→3, 08 204행 · SCRUM-207 ★L-1 case 23 TYPO draft 1·3·3·3·3) 을 흡수한다. `Judge` 생성자 `votes: int = 1` 이 기본값이고 `verify_service.build` 만 `votes=JUDGE_VOTES` 로 만든다 — **초안 안 평가자**(`draft_service.build` 의 `Judge(... schema_retry=0)`)는 `votes=1` 그대로 유지(초안 호출 상한 4 와 "작성 보조는 빠르게" 원칙, 09 2026-11-12 알고 남김).

**집계 규칙**:
- 성공한 호출(스키마 재시도 1 포함) **≥ 2** → 항목별 중앙값. 짝수(2 성공)면 **두 값 중 낮은 점수** (평가자는 엄격 쪽).
- 성공 **< 2** → `VERIFY_UNAVAILABLE` ("중앙값" 효과 소실, 이름과 다른 판정은 안 함).
- `BudgetExceeded` (`insufficient_quota`) 한 호출이라도 → **즉시 전체 중단 · `VERIFY_UNAVAILABLE`** (일 토큰 한도는 재시도로 안 풀림, 남은 future `cancel`).
- `LlmUnavailable` (429 rate_limit·연결 오류) 한 호출 → 그 호출만 포기, 남은 호출로 집계 진행.

**comment·sections**:
- comment: 항목별로 "그 항목 점수 = 중앙값" 을 낸 호출 중 **run 번호 작은 쪽** (`run 1→2→3` 순서). 항목마다 다른 호출 comment 가 섞일 수 있음 — 한 항목 = 한 호출 comment 라 모델 섞임 아님.
- `narrative_refs(sections)`: **run 1 호출의 sections** 그대로. judge_v2 cites 는 "검사한 본문이 실제로 쓴 fact 키" 라 셋 중 어느 것이든 fact_keys 밖은 코드가 버림 — 하나 고정이 집계 규칙 복잡하게 안 함.

**`judge_meta`** (SCRUM-144·92 규칙 그대로 확장):
- `tokens_in`·`tokens_out`: **응답 받은 호출 전부(스키마 실패 포함) 합**. 각 호출 `JudgeResult.meta` 또는 `exc.judge_meta` 의 토큰 더함.
- `latency_ms`: **가장 긴 호출의 지연** (병렬 wall-clock 과 같음).
- `attempts`: submit 수 + 각 호출의 재시도 추가분 합 (각 1~2, 범위 3~6).
- `llm_model`·`prompt_version`: 같은 모델이라 그대로, 혹시 달라지면 run 1 값.
- `verification_runs.judge_*` 저장값은 같은 규칙 (스키마 변경 없음).
- **성공 < 2 (`VERIFY_UNAVAILABLE`) 와 `BudgetExceeded` 경로**도 같은 방식으로 **응답 받은 호출의 meta 를 예외에 붙여** 올린다(`run_votes` 가 `exc.judge_meta` 로 attach, SCRUM-207 Codex 재검토). `verify_service._decide` 가 `getattr(exc, "judge_meta", None)` 으로 받아 `verification_runs.judge_*` 에 저장 — 비용 기록이 null 로 끊기지 않음.

**병렬 · deadline**: `concurrent.futures.ThreadPoolExecutor(max_workers=JUDGE_VOTES)` 를 **직접** 만들고 `try/finally` 로 **`shutdown(wait=False, cancel_futures=True)`**. `with` 블록은 나갈 때 돌고 있는 스레드를 기다려 deadline 을 넘긴다. `as_completed(futures, timeout=남은_시간)` 로 모으고 TimeoutError 면 미완료 future 는 `cancel()` — **이미 돌고 있는 호출은 cancel 로 안 멈추므로 httpx 타임아웃**(`llm_timeout_s`) 으로 자른다. 늦게 돌아오는 호출의 토큰은 집계에 안 섞임(이미 verify 응답이 나간 뒤이고 future 결과를 안 읽으니 공급자 로그로만 남음 — 09 알고 남김 ④).

각 submit 은 **`contextvars.copy_context()` 를 지녀** ballot 스레드까지 `request_id` ContextVar 가 전파된다(SCRUM-207 Codex 재검토). 세 호출의 `llm_call`·`judge_invalid_output` 로그가 상위 request_id 와 묶여 `verification_runs.request_id` 와 교차 조회 가능.

**녹화**: 같은 user → `recording_key` 같음 → 세 호출 다 같은 응답. 녹화 재생 테스트는 그대로 통과(`judge_attempts=3` 만 바뀜). 중앙값·집계·실패 분기는 가짜 LLM 로 단위 테스트(`test_judge_votes.py`·`test_judge_votes_deadline.py`).

## 수정본 길이와 글자 수 (노션 백엔드 미결 24, 규약 §5.3 — 10/30 확정)

- **생성**(`NarrativeOut`, LLM 출력)은 섹션당 1~1,200자 그대로. **검증 요청의 수정본**(조사역이 고친 본문)은 스키마를 따로 두고 섹션당 **최대 5,000자** — 백엔드가 5,000자까지 저장하므로 생성 스키마로 검증하면 1,201~5,000자 수정본이 400이 된다.
- 글자 수는 **NFC로 정규화한 뒤 UTF-16 코드 단위**로 센다 — Java `String.length()`·JS `.length`와 같은 값. Python `len()`·Pydantic `max_length`는 코드포인트라 쓰지 않는다(예: `len(unicodedata.normalize("NFC", s).encode("utf-16-le")) // 2`). 한글·영문은 어느 방식이든 같고, 이모지처럼 BMP 밖 문자만 2로 세진다. 맥에서 NFD로 들어온 한글도 NFC로 바꾼 뒤 세므로 한 글자 = 1.
- NFC는 **세기 위해서만** 쓴다. 해시는 원래대로 `shared/01` 규칙(NFC 포함)이고, 공백 strip은 하지 않는다(10/29 SCRUM-16).
- 경계 테스트(양쪽 리포 같은 값): **5,000자 통과 · 5,001자 400 · "4,999자 + 이모지 1개" 400**(5,001로 셈). 구현은 SCRUM-46.
- 구현 위치: `shared/schemas/str/narrative.NarrativeSectionBase`(공통 부모) + `shared/schemas/str/verify.RevisedNarrativeSection`(5,000자, `_text_within_revised_max`), 세기 함수 `shared/text.utf16_len_nfc`, 상수 `shared/schemas/str/verify.REVISED_TEXT_MAX`. `VerifyRequest.narrative`는 `list[RevisedNarrativeSection]`.

1. 평가자 `judge_v2`가 루브릭 5개와 함께 섹션별 `cites`(검사한 본문이 실제로 쓴 fact 키)를 낸다(`05`). **sections 섹션 집합은 요청 본문과 정확히 같게**(v1 6 또는 v2 7, 섹션마다 1회) — 다르면 `LlmInvalidOutput` → 기존 1회 재시도(SCRUM-92) → 실패면 `VERIFY_UNAVAILABLE`(SCRUM-61 ★A 1).
2. 코드가 `fact_keys(draft.facts)` **밖** 키를 버리고 `attach_evidence(요청 본문 text + 버린 뒤 cites, facts)`로 `evidence_ids`를 만든다 — 생성 때와 같은 함수. **버린 키는 `log.warning("judge_cites_dropped", extra={"section": …, "count": …})` 로 한 줄만**(섹션당 한 번, 키 이름·본문 안 찍음 — CLAUDE.md 로그 금지어, SCRUM-61 ★A 3). 응답 모양은 그대로(규약 5.3 변경 없음).
3. 검증 응답 `narrative_refs: [{section, cites, evidence_ids}]`(**요청 섹션 순서 유지**, v1 6 또는 v2 7)에 담는다. **빈 cites 허용**(평가자가 그 섹션엔 근거 없다고 판단). 평가자를 안 돌린 경우(`CODE_FAILED` — 코드 검사에서 멈춤, `VERIFY_UNAVAILABLE` — 평가자 호출 실패)는 `null`. **`LLM_FAILED`** 는 **값 있음**(평가자는 돌았음, 점수가 미달일 뿐).
4. 백엔드는 **저장하지 않고 읽을 때 반영한다**. 수정본·S4 이력은 사람이 고친 기록만 담고, 근거는 조회할 때 지금 본문 해시와 같은 `narrative_sha256` 의 최신 검증 `narrative_refs` 를 우선 쓰고, 그 값이 `null` 이면 수정본에 저장된 `cites`·`evidence_ids` 로 대체한다(백엔드 #95 `CurrentNarrative`, 11/10 진희). 조사역은 문장만 고치고 근거 번호는 서버가 관리한다.

본문 해시는 section·text만 보므로 `cites`가 바뀌어도 `ApprovalGate`에는 영향이 없다. `EVIDENCE_IN_SCOPE` 코드 검사는 그대로 요청에 담긴 수정본의 `cites`·`evidence_ids`를 본다(재계산 전 값). 테스트: 재계산 결과가 범위 안인지, 목록 밖 키가 버려지는지, `CODE_FAILED`·`VERIFY_UNAVAILABLE`이면 `null`·`LLM_FAILED` 면 값 있음인지(`08` 단위).

3. **방향 + 지표 — (A) 에 맞춤(추가 검토 1 H3 · 2 H3·H4·H5)**: 질문에서 `말고`·`제외하고`·`빼고`·`외에` 바로 앞 방향 낱말은 지움(배제한 방향) · **지표는 방향만 뺀 키 나머지 그대로**(`amount.USD` ≠ `amount.EUR` · `same_bank_accounts` ≠ `other_bank_accounts`) · **양방향 질문도 검사** — 쓴 방향 키마다 같은 지표의 다른 방향 키가 있어야 함(한쪽만 쓰면 실패) · **0건 정정은 정정 절에만** — 질문 방향 0건 건수 키가 반대 방향 키보다 **앞에** 있고, 반대 방향 키가 든 문장(LLM 글)에 질문 방향 낱말이 없을 때만 그 반대 방향 키를 허용. 아래는 추가 검토 1 때 규칙(위로 대체된 곳 포함):

| 5 | 방향 없는 상대 수는 `counterparties.count`·`paths.max_accounts`(VERIFIED) 어느 쪽과 같아도 match(질문 답변은 SCRUM-362 부터 방향이 키 이름표에 — 위 "질문 답변") | `개·곳` 단위가 상대 수·경로 계좌 수 둘 다 될 수 있어 같은 집합으로 대조 | 상대 3·경로 계좌 4 인데 "상대 계좌는 4개" | 슬롯은 종류별로 따로 씀 — 위와 같음 |
| 6 | 관측값은 `observations[].value` 어느 것과 같아도 match(관측값 둘 이상) | 문장에서 어느 숫자가 어느 관측값인지 가리지 않고 관측값 집합과 대조 | 관측값 3·4 인데 두 문장의 값을 서로 바꿔 씀 | 슬롯은 관측값마다 한 문장 — 위와 같음 |
| 7 | 결제 방식 Bitcoin 건수는 COUNT ⑥ 이 못 읽어 방향 없는 거래 건수 집합과 대조(SCRUM-131 4/n) | 별칭을 안 넣음 — `비트코인` 이 통화 BTC 별칭과 겹치고, 통화 건수(방향별)와 결제 방식 건수(입출금 합)의 집계 단위가 달라 넣으면 맞는 문장이 MISMATCH(`비트코인(BTC) 3건` — 11.6 시도에서 확인). ops 데이터 Bitcoin 결제·통화 불일치 2,138행(받은 쪽 약 1.4%) | 실제 Bitcoin 1건인데 `비트코인 2건`(거래 건수 집합 {0,1,2,4} 안) | v4 는 Bitcoin 을 건수 없이 이름만 써서 해당 없음 |

변조 표 분류 코드에는 갈래가 하나 더 있다 — "COUNT 방향 건수는 총건수·통화별 건수 어느 쪽과 같아도 match"(같은 원리). 2차 구조 변경 뒤 변조 표에서 0건이라 표에서 뺐다.

v2 자유 문장에서 같은 원리로 생기는 반례(숫자 우회·플래그 변형·추측·전제 위반·부재·범위 과장)는 `08` "v2 반례 측정(SCRUM-131 3/n)". v4 는 숫자를 슬롯만 쓰고 카탈로그 문장에 숫자가 없어 처음 값은 맞는다 — 남는 위험은 조사역이 고친 수정본이다(검사기를 다시 돌려도 위 1~6 은 통과).

## RAG와의 관계

프롬프트 규칙 8(REFERENCES 숫자·이름 반입 금지)이 1차 방어, `AMOUNT_MATCH`·`DATE_MATCH`·`NO_UNSUPPORTED_CLAIM`이 2차 방어. 코드는 바뀌지 않는다 — 참고 사례의 금액도 "facts에 없는 통화·금액"이라 그대로 잡힌다. 오류 주입 13·14.
